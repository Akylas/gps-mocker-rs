# Shipping the Android app

What is already in place, and what a human still has to do, to get GPS Mocker
into [IzzyOnDroid](https://apt.izzysoft.de/fdroid/) and then
[F-Droid](https://f-droid.org/).

---

## What the repository already provides

| thing                                                     | where                                              |
| --------------------------------------------------------- | -------------------------------------------------- |
| store listing, per language                                | `fastlane/metadata/android/{en-US,fr-FR}/`          |
| icon, feature graphic, phone screenshots                   | `.../images/`                                       |
| per-release changelog, named after the `versionCode`       | `.../changelogs/<code>.txt`                         |
| a signed universal APK on every GitHub release             | `.github/workflows/release.yml` → `gps-mocker-android.apk` |
| an F-Droid build recipe to submit                          | `fdroid/com.akylas.gpsmocker.yml`                   |

The changelog file is written by `tools/fdroid-changelog.mjs`, which
`standard-version` runs as a `postchangelog` hook (see `.versionrc.js`). Cutting
a release therefore produces its own store changelog; nothing has to be
remembered. To write one by hand for the version currently in
`src-tauri/Cargo.toml`:

```bash
node tools/fdroid-changelog.mjs
```

The images are regenerated by `tools/screenshots.mjs`, which drives the real app
in a headless browser — see [Screenshots](#screenshots) below.

### versionCode

Android orders updates by `versionCode`, an integer. The Tauri CLI derives it
from the version in `src-tauri/Cargo.toml`:

```
versionCode = major × 1000000 + minor × 1000 + patch
```

so `2.2.0` is `2002000`. `tools/fdroid-changelog.mjs` uses the same formula to
name its output. It only ever increases, which is what both repositories check.

## IzzyOnDroid first

IzzyOnDroid takes the APK straight off the GitHub release, so there is no build
to get working — which makes it the right one to do first. It reads the same
`fastlane/` tree, so the listing comes out identical to F-Droid's.

Requirements, all of which this repository already meets:

- **A release APK with a stable asset name.** `gps-mocker-android.apk`, attached
  by the release workflow. The desktop app looks it up by that name too, so it
  is not going to drift.
- **A stable signing key.** The four `ANDROID_*` repository secrets. Without
  them the Android job is skipped entirely and no APK is published, which is
  deliberate: a debug-signed APK carries a different key on every run, and
  Android refuses that as an update.
- **A release build that is not debuggable and does not allow cleartext.** Both
  are set in `src-tauri/gen/android/app/build.gradle.kts`.
- **No proprietary tracking libraries.** There are none; IzzyOnDroid scans for
  them and lists what it finds.
- **A licence file and a source repository.** MIT, at the root.

To request inclusion, open an issue on
<https://gitlab.com/IzzyOnDroid/repo/-/issues> using their *Inclusion request*
template, pointing at:

- the repository, `https://github.com/Akylas/gps-mocker-rs`
- the release APK asset name, `gps-mocker-android.apk`
- the applicationId, `com.akylas.gpsmocker`

Once accepted, every new GitHub release is picked up automatically.

### The permissions will be asked about

Two of them look alarming out of context, so it is worth saying so in the
request before anyone has to ask:

- `ACCESS_MOCK_LOCATION` is not granted at runtime. Declaring it is what makes
  the app appear in *Developer options → Select mock location app*, which is the
  only way Android allows any of this.
- `MockControlReceiver` is exported, and guarded by `WRITE_SECURE_SETTINGS` — a
  permission the adb shell holds and no installable app can be granted. It is
  the desktop app's control surface, reachable from a developer's own machine
  and from nothing else on the device.

## F-Droid after that

F-Droid builds from source on its own infrastructure and signs with its own key,
which is stricter and slower. Two things to know before starting:

**A user cannot switch between the two builds in place.** An F-Droid build is
signed with F-Droid's key and a release build with the project's, so installing
one over the other fails with `INSTALL_FAILED_UPDATE_INCOMPATIBLE`. That also
means the desktop app's *Prepare Device* — which installs the release APK — will
refuse a device that already has the F-Droid build, and vice versa.

**The build recipe is the work.** `fdroid/com.akylas.gpsmocker.yml` is a
starting point: Rust cross-compiled to four Android targets, an NDK, and an npm
frontend build, none of which the default gradle path covers. Iterate on it
locally with the buildserver before opening anything:

```bash
git clone https://gitlab.com/fdroid/fdroiddata
cp fdroid/com.akylas.gpsmocker.yml fdroiddata/metadata/
cd fdroiddata && fdroid build com.akylas.gpsmocker
```

Then open a merge request against
[fdroiddata](https://gitlab.com/fdroid/fdroiddata) with the metadata file, and
follow the
[inclusion policy](https://f-droid.org/docs/Inclusion_Policy/).

### The anti-feature

The listing declares `NonFreeNet`, and should: route building, map matching,
place search and the basemap are fetched from online services. Both endpoints
are configurable — Settings → Valhalla endpoint, and Settings → Map — so a
self-hosted Valhalla and any MapLibre style work, but the defaults are
third-party and F-Droid labels that.

## Screenshots

`tools/screenshots.mjs` regenerates every image the website, the README and the
store listings use. It drives the real app — the same Svelte frontend the
desktop and Android builds render — in a headless Chromium over the DevTools
protocol: it plots waypoints by clicking the map, waits for Valhalla to answer,
starts playback, and captures the result.

```bash
npm run dev:web            # in one terminal
npm run screenshots        # in another
```

One shot at a time, by name:

```bash
node tools/screenshots.mjs desktop-terrain
```

It needs a Chromium or Chrome on the machine (set `CHROMIUM` to point at one)
and network, for the map tiles and the routing. Phone shots build their route at
desktop metrics and only then narrow the viewport, because the compact shell
deliberately ignores map clicks — on a touchscreen there is no tap that is not
also the start of a pan.

The store's feature graphic is `tools/feature-graphic.html`, rendered by the
same script. It is a web page so that changing the wording is an edit rather
than a round trip through a design tool.
